# 后端项目验收与生产风险审计

## 核心原则

后端验收先证明“实现了被授权的业务”，再证明“在失败、重试、并发、越权和多实例下仍保持不变量”。不能把编译、单测、`-race` 或静态扫描单独当作生产准入；不能补写不存在的业务规则，也不能用猜测填空。

## 事实与不变量

先收集需求、API schema、状态机、权限矩阵、数据库迁移/索引、外部依赖契约、SLO 和历史事故。建立：

- **来源表**：每个业务规则注明来源、实现位置、反例测试；无来源的 AI 规则（如 VIP 折扣、默认权限、隐式重试）必须删除或阻断。
- **不变量表**：库存不为负、金额可对账、状态只能合法迁移、一次幂等键只有一个最终结果、租户/资源不可越权、失败不产生半成功副作用。
- **追踪矩阵**：入口→handler/controller→service/use case→repository/ORM→事务/锁→外部调用→事件/任务→响应；每层记录成功、失败、超时和取消路径。

## 强制验收顺序

1. **范围和可运行性**：锁定 commit、语言/框架/依赖版本、配置来源、数据库/队列/支付沙箱。环境不可用时将依赖链标为未验证，不能给全绿结论。
2. **需求与逻辑**：逐 API 对照授权需求，检查输入域、状态转换、金额/时间/数量边界、顺序约束、重复/回放、速率和资源上限。识别“看似合理但无来源”的业务分支。
3. **调用链与错误**：逐层追踪错误是否保留语义、是否泄露内部信息、是否在重试后重复副作用、是否吞掉取消/超时、是否留下悬挂 goroutine/promise/worker。
4. **数据与事务**：确认事务边界覆盖一个业务原子操作；外部副作用不假装受数据库事务保护；检查隔离级别、锁顺序、死锁/序列化失败重试、原子条件更新、唯一约束、迁移回滚、读写一致性和 outbox/补偿。支付、库存、订单必须能对账。
5. **幂等与并发**：进程内 Map/单机锁不能承担跨实例或重启后的幂等；幂等键、状态和响应必须持久化并有唯一约束。用并发、重试、超时后重放、进程重启、主从/队列重投验证 exactly-once 需求是否被错误声称。
6. **权限与安全**：鉴权不等于授权；检查功能级、对象级、字段级、租户级、状态级和二次确认授权。覆盖 IDOR、注入、SSRF、反序列化、路径穿越、密钥、日志隐私、CSRF/CORS、上传和资源耗尽；拒绝只测 401/403 而不测“有权用户访问他人资源”。
7. **数据库与性能**：检查查询谓词/排序/连接与复合索引顺序一致，使用 EXPLAIN/真实数据量验证；排查 N+1、全表扫描、深分页、热 key、连接池、超时、批量大小、内存峰值、队列积压、下游重试放大和无界并发。用目标 QPS/数据量/SLO 给出测量结果或明确未验证。
8. **测试证据**：补足单元、契约、集成、真实数据库/容器、并发/竞态、故障注入、fuzz、回放、迁移和安全测试。Go 项目按需路由 `go-review`、`go-enterprise-quality`、`go-testing`、`go-data-consistency`、`go-security`、`go-database-patterns`、`go-stability-engineering` 和 `go-microservice`；PHP/Node 读取对应 `senior-*` skill 并使用框架原生测试/静态工具。
9. **准入**：Blocker/Critical 任一存在，关键不变量无证据，或 DB/支付/队列等核心依赖不可测，结论为 **不准入**。High 必须修复，或记录风险接受者、截止时间、监控、回滚和补测条件；未知项不能默认为通过。

## 必查反例

- 并发扣库存、余额、优惠券、配额：读改写是否原子，是否有唯一约束/锁/版本条件，失败是否释放或补偿。
- 订单/支付：支付超时、重复回调、回调乱序、扣款成功但提交失败、提交成功但响应丢失、退款和对账。
- 幂等：同键不同请求体、并发首请求、处理中重试、完成后重放、缓存/数据库/进程重启、多实例路由。
- 权限：跨租户 ID、资源所有者、管理员自操作、已归档/已支付状态、字段级写入和批量接口。
- AI 规则：需求没有定义的折扣、默认角色、状态跳转、自动补偿、软删除或“最多一次”声明。

## 报告格式

```text
范围：语言/版本/commit/环境/依赖可用性
需求与规则来源：已证实/推测/未确认；覆盖 X/Y
调用链与不变量：逐条证据、反例、缺口
事务/幂等/并发：测试模型、结果、数据约束
权限/安全：身份、对象、字段、租户和状态级结果
数据库/性能：SQL/EXPLAIN、数据量、QPS、p95/p99、资源预算
问题：严重级别、位置、影响、复现、修复验收条件
未验证：原因、风险、补测条件
结论：准入 / 有条件准入 / 不准入
```

## 防止过度承诺

- “race 通过”只覆盖执行到的 Go 代码和测试调度；它不证明 SQL 事务、跨进程竞态、业务不变量或 PHP/Node 的异步/队列行为。
- mock 不证明真实数据库、锁、索引、支付或消息语义；无法连接外部依赖时必须保留阻断项。
- 只要缺少需求来源、关键失败路径或生产数据量，就不能声称“无隐藏 bug/无漏洞/全部覆盖”；报告要量化已覆盖范围并列出未知。
