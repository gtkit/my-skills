# 技术方案与评审

把方案写成可核对的数字与可回答的问题，让评审有对象、上线有退路。与 `senior-go-engineer` 的分工：那边给 Go 的架构判断，这里给文档模板、估算公式与评审清单。

## 核心规则

1. 方案至少有 2 个候选并给对比表；只有一个候选的文档是实现说明，不是方案。
2. 必须写非目标：明确本期不做什么、哪些指标不承诺；没有非目标的方案无法评审范围蔓延。
3. 容量用数字：峰值 QPS、数据量、连接数、带宽、内存，每个数字写出推导公式与输入假设；"够用"、"很大"、"应该没问题"一律退回。
4. 每个外部依赖写明超时值、重试策略、失败降级、观测指标；缺一项视为该依赖未设计。
5. 上线方案包含灰度步骤、每步观察指标与回滚触发条件、回滚操作步骤；数据迁移必须可重复执行且可回滚。
6. 一致性模型必须显式声明：强一致 / 读己之写 / 最终一致，以及最终一致的最大不一致窗口。
7. 金额、汇率、数量精度字段用整数最小单位或 decimal 类型，方案里出现 float/double 存金额直接否决。
8. 依赖方（下游服务负责人、DBA、运维）在方案中列名并确认过容量与时间；未确认的依赖视为风险项。
9. 评审意见分三级（阻塞 / 建议 / 备注），结论只有"通过 / 有条件通过 / 打回"三种，有条件通过必须列出条件、负责人、期限。
10. 文档改动规模达到下表"完整方案"档才写完整文档，否则用 ADR 或 PR 描述，不为小改动写长文档。

## 何时需要完整方案文档

| 改动特征（满足任一） | 文档形态 |
|---|---|
| 新增服务、新增中间件、新增外部依赖；数据模型变更（加表、改主键、拆表）；不可逆操作（删数据、改协议字段序号、换存储）；影响 ≥ 2 个团队；预计工期 ≥ 2 周 | 完整方案文档 |
| 单一技术决策需要留下理由（选库、选协议、选一致性模型、放弃某方案） | ADR |
| 单服务内部改动、不改数据模型、不改对外契约、可用一次部署回滚 | PR 描述写清目标、影响面、验证方式、回滚方式 |

## 技术方案文档模板

| 章节 | 必须回答的问题 | 常见错误写法 |
|---|---|---|
| 1. 背景与问题 | 现在哪个指标不达标（数字）？谁受影响？不解决的代价是什么？ | 只写"业务发展需要"，没有当前数字 |
| 2. 目标与非目标 | 上线后哪个指标到多少（可测量）？本期明确不做什么？不承诺什么？ | 目标写成功能列表；缺非目标 |
| 3. 术语 | 文档中有歧义的名词各指什么？ | 同一个词在不同章节指不同东西 |
| 4. 现状与约束 | 现有架构图、现有容量数字、不能改的部分（协议、期限、预算、合规） | 约束靠读者脑补 |
| 5. 方案 | ≥ 2 个候选；对比表维度：正确性风险、容量上限、开发成本、运维成本、可回滚性、对现有系统的改动面；推荐哪个及理由 | 只有一个方案；对比表只有"优/劣"没有依据 |
| 6. 详细设计 | 数据模型（表结构、索引、预计行数与增长）；接口契约（请求/响应、错误码、幂等键、超时）；关键时序图；状态机（状态、迁移条件、非法迁移如何处理）；容量估算（见下节）；一致性模型与每个失败点的后果 | 缺失败模式；状态机只有正常路径 |
| 7. 依赖与风险 | 依赖哪些服务/团队/组件，各自负责人是否确认；每条风险的触发条件、影响、缓解措施、负责人 | 风险写"可能有性能问题"没有缓解措施 |
| 8. 可观测性与告警 | 新增哪些 metrics、日志字段、trace span；告警阈值多少、通知谁 | 上线后才想起加监控 |
| 9. 测试与验收 | 单测覆盖哪些边界；集成测试覆盖哪些失败注入；压测目标数字；验收标准由谁确认 | 验收标准写"功能正常" |
| 10. 上线计划 | 灰度分几步、每步流量比例、每步观察哪些指标多久；回滚触发条件与操作步骤；预案（依赖故障怎么办）；数据迁移的执行、校验、回滚脚本 | 只有"先灰度再全量"，没有触发条件 |
| 11. 里程碑 | 每个里程碑的交付物、验收方式、日期、负责人 | 只有一个"上线日期" |
| 12. 待决问题 | 尚未定的事项、需要谁在什么时间前决定 | 把待决问题藏在正文里 |

## ADR 模板

用于记录单个技术决策，一页以内，放在仓库 `docs/adr/NNNN-标题.md`，编号递增、只追加不修改（被推翻时新建一条并在旧条标注"已被 NNNN 取代"）。

```
# ADR-0007：订单事件投递采用 outbox 表而非双写 MQ
状态：已采纳 / 已取代（by ADR-NNNN） / 已废弃      日期：2026-08-28
背景：需要在订单落库后向下游投递事件，双写 MQ 在 DB 提交后 MQ 发送失败时丢事件。
决策：订单事务内写 outbox 表，独立投递进程轮询投递，消费方按 event_id 幂等。
备选：(1) 先发 MQ 再落库——MQ 成功 DB 失败会产生幽灵事件；(2) 事务消息——当前 MQ 不支持。
后果：多一张表与一个投递进程；事件延迟增加约 100–500ms；下游必须实现幂等。
```

何时用 ADR：选存储/协议/一致性模型、放弃某个方案、引入或移除一个依赖、决定"不做"某件事。

## 容量估算方法

估算给出量级与瓶颈位置，压测给出真实值；两者差超过 2 倍时先解释差异再定副本数。

| 项目 | 公式 | 示例 |
|---|---|---|
| 平均 QPS | 日活 × 人均日请求数 ÷ 86400 | 200 万 × 30 ÷ 86400 ≈ 694 |
| 峰值 QPS | 平均 × 峰值系数；常规业务按 80% 请求集中在 20% 时间取 4；有定时推送/秒杀取 10 以上，以历史监控为准 | 694 × 4 ≈ 2800 |
| 设计目标 QPS | 峰值 × 12 个月增长系数 | 2800 × 1.5 = 4200 |
| 并发数（Little 定律） | 并发 = QPS × 平均耗时 | 4200 × 0.05s = 210 个在途请求 |
| 存储总量 | 日新增行 × 行大小 × 索引系数(1.5–2) × 保留天数 × 副本数 | 6000 万行 × 200 B × 1.5 × 180 天 ≈ 3.2 TB，主从 ×2 ≈ 6.4 TB |
| 存储增长 | 日新增行 × 行大小 × 索引系数 | 18 GB/天，单实例 2 TB 盘约 110 天写满 |
| DB 连接数 | Σ(副本数 × 每副本连接池上限) ≤ DB `max_connections` × 0.8 | 30 副本 × 40 = 1200 > MySQL 8 默认 151 / PostgreSQL 默认 100，必须调 DB 参数或缩池 |
| 连接池大小 | 单副本 DB 并发 = 单副本 QPS × 每请求查询数 × 单查询耗时 | 140 QPS × 5 次 × 5ms = 3.5，池上限 10–20 足够 |
| goroutine / 协程预算 | 每在途请求 1 + 下游并发数；每 goroutine 栈初始 2 KiB 且随调用深度增长 | 210 在途 × (1 + 3) ≈ 840，无压力；10 万 goroutine 栈至少 200 MiB，实测常超 1 GB |
| 出口带宽 | QPS × 平均响应体 × 8 | 4200 × 15 KB × 8 ≈ 504 Mbps，接近千兆网卡一半，需压缩或 CDN |
| 缓存内存 | key 数 × (key 长度 + value 长度 + 约 80 B 元数据) | 5000 万 × (50 + 200 + 80) B ≈ 16.5 GB，超单实例合理上限，需集群 |
| MQ 积压与追平 | 积压 = (生产速率 − 消费速率) × 停摆时长；追平时间 = 积压 ÷ (消费能力 − 生产速率) | 消费停 30 分钟：2000/s × 1800s = 360 万条；消费能力 3000/s 追平需 3600s |
| 副本数 | 设计目标 QPS ÷ (单机压测 QPS × 0.7) + 1 | 4200 ÷ (600 × 0.7) + 1 = 11 |

单机压测 QPS 的定义：一个副本在生产同规格上 CPU 达到 70% 时的 QPS，同时 P99 仍满足延迟预算。

## 方案评审清单（评审人用）

每项回答"是 / 否 / 不适用"，回答"否"的项必须出现在评审意见里。

**正确性**
- [ ] 目标指标有当前值与目标值两个数字？
- [ ] 每个接口的幂等键与重复请求的返回值已定义？
- [ ] 状态机列出了全部状态与迁移条件，非法迁移有明确处理？
- [ ] 金额与精度敏感字段使用整数最小单位或 decimal？

**失败模式**
- [ ] 每个外部调用写明了超时值与失败降级？
- [ ] 重试只针对幂等操作，且有总次数上限与退避？
- [ ] 部分成功（写了 A 没写 B）的场景已枚举并有处理方式？
- [ ] 依赖不可用时服务的行为已定义（降级还是快速失败）？

**一致性**
- [ ] 一致性模型（强一致 / 读己之写 / 最终一致）已声明？
- [ ] 最终一致的最大不一致窗口有数字？
- [ ] 跨库/跨服务写操作按"合库 → 异步最终一致 → Saga → TCC"顺序论证过为什么选当前档？
- [ ] 消费端幂等实现已写明（幂等键、去重表或唯一索引）？

**容量**
- [ ] 峰值 QPS、存储、连接数、带宽、内存五项都有公式与输入假设？
- [ ] 连接数总和已与 DB 上限比对？
- [ ] 有单机压测计划与目标数字？
- [ ] 增长系数与保留期已写明？

**可观测**
- [ ] 新增的 metrics 名称、label、告警阈值、接收人已列出？
- [ ] 日志带 request_id / trace_id，关键路径有 span？
- [ ] 灰度期间用来判断"好/坏"的指标已指定？

**安全**
- [ ] 新接口的鉴权方式已写明？
- [ ] 外部输入的校验规则与拒绝行为已定义？
- [ ] 密钥、令牌的存放与轮换方式已写明？
- [ ] 新增的数据字段中的个人信息已标注并有脱敏/保留期？

**可回滚**
- [ ] 回滚触发条件是具体指标阈值？
- [ ] 回滚步骤可在 10 分钟内由值班人执行且已演练？
- [ ] 数据迁移脚本可重复执行（幂等）且有反向脚本？
- [ ] 灰度期间新旧版本共存：协议向后兼容、双写/双读的数据可互读？
- [ ] 配置开关可在不发版的情况下切换新旧路径？

**成本**
- [ ] 新增资源（实例、存储、带宽、许可）有月度成本估算？
- [ ] 运维成本（值班、升级、备份）有归属团队？
- [ ] 方案对比表中的开发成本以人日估算？

## 常见评审否决项

- 没有非目标——范围无法评审，后续任何需求都能塞进来。
- 只有一个候选方案——没有对比就没有"为什么是它"。
- 没有回滚方案或回滚步骤未演练——出问题时只能硬扛。
- 容量用"够用"、"很大"、"应该没问题"描述——无法核对，也无法在上线后验证。
- 金额用 float/double——二进制浮点表示不了 0.1，累加误差不可控。
- 一致性模型未声明——评审人无法判断哪些读到旧值的场景是 bug。
- 依赖方未确认——下游容量、DBA 变更窗口、运维资源都是假设。
- 外部调用没有超时值——默认值多为无限，下游 hang 住会拖垮本服务。
- 数据迁移不可重复执行——中途失败后既不能重跑也不能回退。
- 灰度期间新旧版本不兼容——灰度本身会制造故障。
- 上线后才补监控——灰度期间没有判断好坏的依据。
- 状态机只有正常路径——异常迁移在生产上一定会出现。

## 评审沟通

**意见分级**

| 级别 | 含义 | 处理 |
|---|---|---|
| 阻塞 | 不改就不能上线：正确性错误、无回滚、容量缺失、一致性未声明、安全缺口 | 必须修改并复审 |
| 建议 | 改了更好但不阻塞：更优的候选、可简化的设计、可省的成本 | 作者决定采纳与否并回复理由 |
| 备注 | 措辞、图示、格式、待确认的小疑问 | 作者自行处理，不需要回复 |

**结论记录**（写在文档末尾，逐次追加）

```
评审 #2  2026-08-28  评审人：A、B、C
结论：有条件通过
条件：(1) 补充 outbox 投递进程的告警阈值——负责人 X，8-30 前；(2) 连接池上限从 40 降到 20 并更新连接数估算——负责人 Y，8-29 前
阻塞项：无     建议项：3（见评论 #12 #15 #18）     备注项：5
```

评审会前 24 小时发出文档，评审人书面提交意见；会上只讨论阻塞项与有分歧的建议项，每项给出结论与负责人，会后 1 个工作日内更新文档并回复所有意见。

## 文档审查清单（作者自查）

- [ ] 第 1 节有当前指标数字，第 2 节有目标数字与非目标列表
- [ ] 第 5 节至少 2 个候选，对比表维度包含正确性风险、容量上限、开发成本、运维成本、可回滚性、改动面
- [ ] 第 6 节容量估算每项有公式、输入假设、结果，与"容量估算方法"表逐项对应
- [ ] 每个外部依赖写了超时、重试、降级、观测四项
- [ ] 每个状态机列出全部状态与非法迁移处理
- [ ] 第 7 节每条风险有触发条件、影响、缓解措施、负责人；每个依赖方有确认记录
- [ ] 第 10 节灰度每步有流量比例、观察指标、观察时长、回滚触发条件；迁移脚本有幂等与反向脚本
- [ ] 第 11 节每个里程碑有交付物、验收方式、日期、负责人
- [ ] 全文没有"够用"、"很大"、"应该没问题"、"后续再优化"这类无数字表述
- [ ] 金额与精度字段类型已核对
- [ ] 文档改动规模符合"何时需要完整方案文档"的判定，没有为小改动写长文档
